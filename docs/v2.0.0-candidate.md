# v2.0.0 Candidate: Evidence-First Developer Launch

This page is a candidate-readiness summary, not a release announcement. It
describes what an Agent Foundry developer can use from the accepted
integration, what the evidence does not establish, and which gates remain
before `main`, a tag, or a production claim.

The candidate is finalized only on
`codex/orch-05-single-active-handoff-integration`. This non-`main` line is the
current authority for closeout Work; the older
`codex/v2-local-first-orchestration` line is historical. Documentation or
integration acceptance does not authorize a merge to `main`, tag, release,
runtime/adapter publication or public-readiness claim.

AF17 and AF18 are completed pre-V2 enabling foundations already integrated into
`main`. V2 consumes their semantic-loading, adapter-reachability and bounded
collaboration foundation by ancestry; they are neither ORCH milestones nor
active V2 completion work. Any AF19 follow-up is separately scoped.

## First success

Ask for **“开启本地多-agent协作”** / **“start local collaboration”**. The
supported first path is SQLite-backed, single-machine collaboration:

1. Run a read-only owner preflight for onboarding, current authority and
   status.
2. Read the owner-provided safe next action. If it mutates state, make the
   required Human decision explicitly.
3. After an approved operation, use fresh owner readback; use the optional
   Board only as a read-only view.
4. Use the owner-guided backup, restore, takeover, source-lock and cleanup
   guidance for recovery. Do not invent a repair or a second store.

See [Local Collaboration Lifecycle](../workflows/local-collaboration-lifecycle.md)
and [Multi-Agent Collaboration](multi-agent-collaboration.md).

For the separate first-use request **“开启多agent协作”**, success has a stricter
postcondition: it names the bound project, records whether durable Coordinator
and Architect roles were reused, created or held, verifies a durable
scheduler/Work-root binding, and distinguishes native role onboarding from
repository-contract-only setup. Missing or ambiguous evidence is a hold, not
`initialized`. [#548](https://github.com/farmerhunter/agent-foundry/issues/548)
and [#549](https://github.com/farmerhunter/agent-foundry/issues/549) preserve
historical defect/governance evidence; the accepted retained-authority readback
establishes the current owner-recorded postcondition, so their open issue state
is not an unresolved current capability blocker and is not permission to create
missing state manually.

## Evidence-backed capability boundary

| Area | Candidate status | Meaning |
| --- | --- | --- |
| Base practice/asset/issue/PR workflows | `supported_default` | Stateless or GitHub-first workflows remain supported without enabling Local Orchestration. |
| SQLite single-machine onboarding, status and recovery | `available` | Accepted Core/integration evidence supports the owner-guided path; it is not a production shipment claim. |
| Owner-bound local action and exact duplicate handling | `available` | Mutation remains explicitly Human-gated and ends with owner readback. |
| A0-Lite handoff | `experimental_same_host_manual_custody` | Two isolated authorities on one host, immutable manual custody, source lock, target-local activation and recovery evidence. |
| GitHub facts and Project views | `non_authoritative_projection` | Native collaboration facts or optional projections; neither replaces SQLite authority. |
| ORCH-03 remote materialization | `candidate_or_optional` | No automatic materialization, Project projection, remote write or convergence promise. |

The completed functional walkthrough establishes the lifecycle/front-door
boundary. It does not manufacture usability, performance, latency, scale or
real-adopter-friction metrics; these remain `unknown/not_exposed` until later
real usage feedback.

The accepted owner receipt records `native_ready`, bound
project/control/scheduler/Work-root state and opaque durable-role references.
It also records `native_reachability=not_checked` and
`mutation_performed=false`. Therefore it does not establish live App Server or
thread reachability, current host-process reachability or cross-host
continuity. Fixture, static, walkthrough and controlled-local results do not
establish UX, performance, real-device resilience, production readiness or
release readiness.

## Explicitly deferred

The candidate does not claim real second-device operation, cross-host handoff,
device-loss resilience, independent credentials, transport, hostile-device
trust, source unlock after an unreturned transfer, or global convergence. Those
requests remain `held_real_second_device_deferred`; do not use A0-Lite or a
Core/Vault snapshot as a workaround.

JSONL/V2 trial and `--ledger-root` surfaces are historical, export or diagnostic
material. They are not a normal onboarding route, a migration requirement, a
fallback authority, or a dual-write path.

## Restore and offline boundary

Core/Vault restore reconstructs product records, generated outputs and local
runtime setup. It does not transfer SQLite collaboration authority. Never copy,
share, mount or synchronize SQLite authority files between machines. Read
[Deployment](deployment.md) and [Offline Sync](offline-sync.md) before any
restore or archive work.

## Remaining gates

- Evidence-first developer documentation must pass independent review, command/
  link/render checks and Human user-facing document review.
- ORCH-04 final readiness remains separate from functional lifecycle evidence.
- A0-Real needs real two-device/cross-host evidence and an explicit Human
  decision.
- Any `main` merge, tag, release, runtime/adapter publication, real transport,
  external materialization or Project write needs its own authorization.

The roadmap records these distinctions in [Roadmap](roadmap.md) and
[ORCH milestones](roadmap/milestones-v2.md).
